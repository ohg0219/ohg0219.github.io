# blog-draft

이 Skill 이 호출되면 다음 절차를 따른다.

## 1. 메타데이터 로드

- `.claude/blog-session.md` 를 읽는다.
- **없으면** 사용자에게 안내하고 종료:
  > "블로깅 세션이 시작되지 않았습니다. 먼저 `/blog-start <주제>` 를 실행하시거나, 지금 주제를 알려주시면 시작 단계 없이 바로 초안을 작성할게요."
  > (사용자가 즉시 주제를 알려주면 그것을 받아 진행하되, `.claude/blog-session.md` 도 함께 생성)
- frontmatter 에서 `topic`, `slug`, `categories`, `tags` 추출.

## 2. 대화 분석

대화 전체를 머릿속에서 다음 네 차원으로 정리한다. 이건 **분석 단계** 일 뿐이고, 본문 라벨에 이 이름들을 그대로 쓰지 않는다 (본문 라벨은 3절의 톤 가이드 참고).

### 발단
- 사용자가 처음 무엇을 하려 했는가
- 어디서 막혔는가 / 어떤 에러·증상이 있었는가
- 환경(OS, 언어/프레임워크 버전 등) 이 대화에 나왔으면 명시

### 시도와 발견
- 의미 있는 시행착오 2~4개 (모든 삽질을 다 적지 말 것)
- 핵심 단서가 된 정보 (로그 한 줄, 문서 한 문장, Stack Overflow 답변 등)
- 가설 → 검증 흐름이 있으면 그 구조를 살린다

### 해결
- 최종적으로 동작한 코드/명령/설정
- 한 가지 방법으로 좁혀서 명확하게. 대안이 있으면 "다른 방법: ..." 으로 짧게만 언급

### 일반화
- 라이브러리·도구 한정 팁이 아니라 사고방식 차원의 교훈
- 다음에 비슷한 상황을 만났을 때 가장 먼저 확인해야 할 한두 가지

## 3. 포스트 파일 생성

`_posts/<category>/<YYYY-MM-DD>-<slug>.md` 를 Write 툴로 새로 만든다. `<category>` 는 frontmatter `categories[0]` 와 **반드시 일치**시킨다 (폴더가 없으면 만든다). 같은 파일이 이미 있으면 slug 뒤에 `-2`, `-3` 을 붙여 충돌 회피.

**Frontmatter**:

```yaml
---
title: "<짧은 제목>"
description: "<부제 또는 한 줄 요약>"   # 선택, 부제가 있는 경우만
date: <YYYY-MM-DD HH:MM:SS +0900>
categories: [<categories>]
tags: [<tags>]
# 다이어그램이 본문에 들어가면 다음 줄 추가:
# mermaid: true
# 시리즈 글이면 다음 블록 추가 (.claude/blog-session.md 의 series 필드 참고):
# series:
#   name: <series-slug>     # _data/series.yml 의 키와 일치
#   part: <N>               # 1, 2, 3...
---
```

`layout: post` 는 적지 않는다 — 블로그 `_config.yml` 의 defaults 가 자동 적용한다.

### title / description 규칙 (중요)

목록·카드·검색·시리즈 nav 어디서나 한눈에 읽히는 짧은 title 을 만든다. 길어지면 description 으로 분리한다.

- **title 은 핵심 키워드만**. 권장 20자 이내, 단독 글도 가급적 25자 이하. **"주제 — 부제 — 시리즈 N편" 같은 이중 em-dash 구조 금지**.
- **부제·요약은 `description:` 필드로 분리**. Chirpy 가 카드 미리보기와 `<meta name="description">` 에 자동 사용한다. (post 본문 상단에는 표시되지 않음 — 본문 도입부가 그 역할을 한다.)
- **시리즈 글의 시리즈 표기는 `[N편]` 접미사로 통일**. `series.part` 번호와 일치시킨다. `— 시리즈 N편` 같은 풀어쓴 형태는 쓰지 않는다 (series-nav.html 의 `<ol>` 이 이미 순서·현재 글을 시각화함).
- description 이 없는 단편이면 줄을 통째로 생략한다. 빈 값 `description: ""` 으로 두지 말 것.

**적용 예시**:

| 패턴 | title | description |
|---|---|---|
| 시리즈, 부제 없음 | `Docker 기초 [1편]` | *(생략)* |
| 시리즈, 부제 있음 | `Docker Compose [3편]` | `여러 컨테이너를 한 파일로` |
| 시리즈, 긴 부제 | `Service 와 네트워크 [4편]` | `Pod IP 가 자꾸 바뀌는데 어떻게 연결하나` |
| 단독, 부제 있음 | `Spring Boot Actuator 헬스체크 함정` | `경로가 root 로 떨어진 이유` |
| 단독, 키워드 위주 | `POI freeze pane 과 활성 셀의 함정` | `Excel 자동 생성 파일이 매번 자체 복구를 띄운 이유` |

**`.claude/blog-session.md` 매핑**:

- `topic` → `title` (필요시 더 짧게 다듬어도 됨)
- `subtitle` (있으면) → `description`
- `series.part` 가 있는 경우 → title 끝에 ` [Npart편]` 자동 부착

**시리즈 글이면 본문 맨 위에 다음 한 줄을 추가한다** (front matter 바로 다음, 리드 단락보다 위):

```liquid
{% include series-nav.html %}
```

이 include 가 같은 `series.name` 을 가진 모든 글을 part 순으로 나열한 박스를 렌더한다. 새로운 시리즈를 시작하는 경우 `_data/series.yml` 에 시리즈 이름·설명을 한 블록 추가한다 (없으면 박스 헤더가 series.name slug 그대로 표시됨).

**본문 구조 — 톤 가이드 (중요)**:

다음 패턴을 따른다. **"문제 상황 / 시도와 발견 / 해결책 / 배운 점" 같은 보고서 라벨은 쓰지 않는다.**

```
(첫 ## 라벨 없이) 리드 단락 1~2개
   ↑ 장면·현상·문제를 한눈에 사로잡는 후킹.
     강조 굵게(**...**) 나 인용(>) 활용 가능.

## <자연스러운 의문문 또는 짧은 서술문>
   예: "어디서 빌드할 것인가", "최소 스켈레톤은 어디까지 줄어드나",
       "환영 페이지가 떴다", "진짜 범인은 한 줄이었다",
       "더 재미있는 건 안쪽이다"

## <다음 흐름 라벨>
...

## 남는 것  /  가져갈 한 줄  /  가져갈 두 가지
   결론부는 부드러운 라벨. "배운 점" 같은 보고서 톤 금지.
```

리드 단락 예시:

> "어제 어디까지 했지?" — AI 페어 프로그래밍을 며칠만 해본 사람이면 한 번쯤 떠올리는 질문입니다. 모델은 어제의 결정을 기억하지 못하고, 사람은 매번 처음부터 설명을 다시 깔아야 합니다.

> **404 도 아니고, 500 도 아니고 — 루트가 떴습니다.** 헬스체크 URL 을 호출했는데 Spring Boot 의 기본 환영 페이지가 떨어진 그날의 디버깅 기록입니다.

라벨에 "—" 부제목 (예: `## Before / After — "AI 와 일한다" 의 의미가 바뀐다`) 은 사용 가능하지만 남용 금지.

## 4. 작성 원칙

- **리드 우선**: 도입 1~2 단락에서 한눈에 흥미를 잡지 못하면 글을 안 읽는다. 가장 강한 문장을 맨 앞에 둔다.
- **톤**: 기본 "~합니다 / ~습니다" 체. 대화에서 사용자가 반말이면 반말로 통일. 본문만 변환하고 코드·로그·에러 메시지는 원문 그대로.
- **사실·코드 보존**: 사실 / 코드 / 명령어 / URL / 로그는 원문 그대로. 톤만 다듬는다.
- **민감 정보 마스킹**: API 키, 비밀번호, 사내 서버 주소·IP, 개인 이메일, 인증 토큰이 발견되면 `sk-xxxx`, `<INTERNAL_HOST>`, `xxx@example.com` 등으로 치환하고 본문에 ⚠️ 한 줄 주석을 남긴다.
- **출처**: 대화 중 등장한 외부 링크 (Stack Overflow, 공식 문서, GitHub Issue) 는 본문 끝 "참고" 섹션에 모은다.
- **코드 블록 언어 태그**: ` ```yaml `, ` ```java `, ` ```powershell ` 등 반드시.
- **시행착오는 의미 있는 1~2개만**. 모든 삽질을 다 적지 않는다.
- **분량**: 800~1500 단어 권장. 너무 길면 frontmatter 직전 HTML 주석으로 `<!-- TODO: 후속편 분리 권장 -->` 남기되 본문은 그대로 작성.

## 5. 사용자 안내

작성 후 다음을 한 번에 출력:

```
📝 초안 작성 완료
   파일: _posts/<category>/<YYYY-MM-DD>-<slug>.md

다음 단계:
  1) 에디터에서 열어 검토·수정 (특히 도입 1~2 단락의 후킹이 충분히 강한지)
  2) 발행:
     git add _posts/<category>/<YYYY-MM-DD>-<slug>.md
     git commit -m "post: <topic>"
     git push

   배포 후 약 1~2분 뒤:
   https://ohg0219.github.io/posts/<slug>/
```

## 6. 부수 동작

- 초안 작성에 성공했으면 `.claude/blog-session.md` 의 frontmatter 에 `drafted_at: <YYYY-MM-DD HH:MM>` 을 추가 (같은 세션에서 재실행 시 추적용).
- 같은 세션에서 두 번째 호출이면 사용자에게 "이미 초안이 있어요(`<기존 파일>`). 1) 덮어쓰기 2) 새 파일로 분리 (`-2` 접미사) 중 어느 쪽?" 을 묻는다.
